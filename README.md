# Dickplomacy
> Generated by Claude

A fully functional web-based implementation of the board game *Diplomacy*.


[Play the game](https://dickplomacy.github.io/game/)

## Overview

Dickplomacy is a browser implementation of classic *Diplomacy*: 7 powers,
34 supply centers, no dice — pure adjudicated movement, support, and
convoy orders. The name is an inside joke — no relation to game mechanics, no house rules
implied unless explicitly stated elsewhere in this repo. See [DIPLOMACY_RULES.md](./DIPLOMACY_RULES.md) 
for the full rules and adjudication reference this implementation follows.

Built with React + Vite, with Firebase (Firestore) as the backend for game
state, real-time multiplayer sync, press messaging, and treaty tracking.

## Resolver (`resolver.js`)

Pure function `resolve(units, orders) → { units, dislodged, ...debugData }`.
No Firestore or React dependency — takes current unit positions and a
per-unit order map, returns new positions plus units needing to retreat.

**Algorithm outline:**
1. **Collect moves** — for each unit with a `move` order, check direct
   adjacency (`isAdjacent`, via `territories.json`). If not adjacent and the
   unit is an army, attempt a convoy chain (`hasConvoyChain`, BFS over sea
   territories occupied by fleets with matching `convoy` orders).
2. **Compute strengths** (`computeStrengths`) — attack strength = 1 + valid
   move-support; hold strength = 1 + valid hold-support. Support is cut if
   the supporter is attacked from anywhere except the territory the
   supported move is aimed at (standard rule — implemented via `cutSupporters`).
3. **Resolve moves** (`resolveWithStrength`) — iterative fixpoint over unit
   statuses (`pending → succeeded/failed`):
   - Head-to-head battles (two units swapping without convoy) resolved
     first, unless either move is convoyed (a convoyed "swap" isn't a real
     head-to-head, per the rules doc)
   - Attacker vs. defender hold strength, with self-dislodgement
     explicitly prevented (a power can't dislodge its own unit)
   - Rivalry checks between multiple attackers on the same destination
   - **Cycle detection** at the end handles circular movement (A→B→C→A):
     if the whole dependency chain loops back to the start with everyone
     still `pending`, all succeed; otherwise all fail
4. **Convoy disruption loop** — after each resolution pass, checks whether
   any fleet providing a convoy was itself dislodged. If so, the chain is
   rechecked excluding dislodged fleets; if no alternate route exists, the
   army's move is cancelled and the whole thing re-resolves. This loop
   converges rather than recursing, and because it starts from "all
   convoys active," circular paradox cases resolve in favor of the convoy
   succeeding (the Szykman-style convention DIPLOMACY_RULES.md calls the
   "standard ruling").
5. **Dislodged units & retreat options** — for each dislodged unit,
   computes valid retreats: excludes the attacker's origin, any square
   contested to a standoff this turn, and any square now occupied by a
   surviving or newly-arrived unit.

**Not yet implemented in the resolver itself:** the actual retreat-order
application and winter adjustments — those live in separate modules
(`adjustments.js`) and presumably a not-yet-seen retreat-resolution path in
`gameService.js`/UI.

## Winter Adjustments (`adjustments.js`)

- `HOME_SCS` — each power's 3–4 home supply centers (needed because builds
  can only happen in *unoccupied, owned* home centers, not any owned SC)
- `computeAdjustments(ownerMap, unitList)` — per power, delta = (supply
  centers owned) − (units on board); positive = can build, negative = must
  disband
- `buildWinterData(...)` — returns `null` if every power's delta is 0 (this
  is how `gameService.js`'s "skip winter" transition is decided); otherwise
  auto-fills empty `{ builds: [], disbands: [] }` orders for powers with no
  adjustment needed, so only powers with a nonzero delta need to act
- `getAvailableBuildSCs(power, ownerMap, unitList)` — valid build sites:
  owned home centers not currently occupied
- `ownersFromUnits(prevOwners, newUnits)` — updates the owner map from unit
  positions after resolution (only touches occupied territories, leaves
  the rest of ownership untouched — since owned-but-unoccupied SCs keep
  their owner)

## Data Model (Firestore)

Each game is a document at `games/{gameCode}`, where `gameCode` is a random
4-letter code (from an unambiguous alphabet excluding `I`/`O`).

```
games/{gameCode}
├── code, phase, year
├── players: { ADMIN, AUSTRIA, ENGLAND, FRANCE, GERMANY, ITALY, RUSSIA, TURKEY }
│     → each value is a secret token; a token is the player's "login"
│       (see getRoleForToken) — no real auth system, just shared secrets
├── units: [{ id, type, power, x, y }]
├── owners: { [territoryId]: power }
├── orders: { [power]: { [unitId]: { type, dest?, target?, army? } } }
├── draftOrders: { [power]: ... }        // unsubmitted, in-progress orders
├── retreatPhase: null | { dislodged, retreatOrders }
├── winterPhase: null | { adjustments, orders }
├── settings: { autoResolve, passivePowers, lockedPowers }
├── lastPhaseLog, history[]
├── winner (once game ends)
└── createdAt / updatedAt

games/{gameCode}/treaties/{treatyId}    // subcollection, synced live
games/{gameCode}/messages/{messageId}   // press subcollection
│     { from, to: string[], body, year, phase, sentAt }
│     to: [] means public/visible to all
```

**Phases:** `spring-move` → `spring-retreat` (if needed) → `fall-move` →
`fall-retreat` (if needed) → `winter` (if needed, decided by
`buildWinterData` returning non-null) → next year's `spring-move`.

**Player tokens:** powers can share a token via `powerSlots` (e.g. one
person plays two countries), and can be marked `passivePowers` (get their
own token, presumably for a lighter/non-strategic role). `lockedPowers`
controls which countries are selectable when joining.
